\section{Initial Capability Baseline}
\label{Section:InitialCapabilityBaseline}
The baseline identifies a signal acquisition pipeline for Embedded Engineers,
with the following owner-supplied connection chain:

\begin{center}
Sensor $\rightarrow$ ADC0804 $\rightarrow$ FTDI245R interface
$\rightarrow$ host computer
\end{center}

This is an initial context statement, not a detailed allocation or implemented
architecture. Supported host operating systems in the initial baseline are
Linux, macOS, and Windows. Implementation and demonstrated compatibility are
not established. The reproducible-code-base objective is defined in
\hyperref[Section:ProjectPurpose]{Purpose}; measurable reproducibility criteria
remain \OwnedTBD{}.

\section{System Boundary and Allocation}
\label{Section:ProjectSystemBoundary}
The system of interest is the FTDI245R data acquisition pipeline code base.
Its hardware--software boundary separates pipeline-owned acquisition software
from the external hardware, platform services, and downstream processing
consumer on which it depends. The ADC0804, the 74xx counter, the peer
FTDI245R, the USB stack, the host operating system across Linux, Windows,
and macOS, and the downstream processing consumer are controlled external
dependencies at this boundary, as directed by the document owner.

These dependencies participate in the acquisition context but their internal
implementations are outside the pipeline code-base boundary. The dependency
register below identifies the contracts that the pipeline must account for
during later requirements and architecture work. The Sensor remains the
upstream external signal source. Its specific identity and connection
characteristics remain \OwnedTBD{}.

Detailed allocation among pipeline software components, firmware,
programmable logic, storage, and display remains \OwnedTBD{}. No counter topology,
device programming model, driver/API, or electrical behavior is inferred.
The term peer FTDI245R identifies the external endpoint specified by the
owner; its physical identity and relationship to the previously named
FTDI245R interface remain \OwnedTBD{}. No additional FTDI245R device is assumed.

\section{Signal Definition}
\label{Section:ProjectSignals}
The source is a Sensor through an ADC0804 connected to the FTDI245R
interface. Each conversion supplies one unsigned 8-bit byte, with no headers
or framing; the downstream consumer receives the same raw bytes. Sampling
is constant, with no increases above the normal rate. The sustained sample
rate is TBD pending ADC0804 timing and hardware confirmation (decision owner:
Joel Murphy and Abtin Khatoonabadi). Signal type, channel count, triggering, ranges, units,
accuracy, clocking, synchronization, and operational calibration remain
TBD (decision co-owners: Joel Murphy and Abtin Khatoonabadi). Acquisition conditions and preservation
boundaries are defined in \hyperref[Section:ProjectAcquisitionConditions]{Requirements}.

\section{Lifecycle Intent}
\label{Section:ProjectLifecycleIntent}
With the required driver/library installed and configuration completed on a
supported host, detection is automatic without a code change and acquisition
starts automatically on first connection. Acquisition continues until the
user stops it. Partial timeouts deliver actual returned bytes in order and
acquisition continues; empty timeouts deliver no bytes and acquisition
continues. Every read requests at least one byte; timeout duration is TBD
(decision co-owners: Joel Murphy and Abtin Khatoonabadi).

Disconnection does not crash or corrupt the pipeline. All bytes successfully
read into host memory before disconnection are delivered unchanged and in
order, including pending bytes. Device-resident bytes and bytes generated
while disconnected are outside the preservation guarantee. The pipeline
reports the interruption without claiming complete acquisition and
automatically resumes on reconnection with the interruption clearly marked.
The owner-approved meanings of \gls{fsareliable}, \gls{fsaplugandplay},
\gls{fsacorruption}, and \gls{fsadelivery} apply.

Reporting interface, reconnection identity/stale device-buffer handling,
consumer failure/backpressure, buffering/overflow, user-stop/drain behavior,
and quantitative reliability targets remain TBD (decision co-owners: Joel Murphy and Abtin Khatoonabadi).
These are approved behavioral decisions translated into candidate
requirements, not an implemented or verified behavior claim.
